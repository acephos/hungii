## Proposed application description and moat

Hungii helps Indian students, early-career workers and people with irregular meal schedules choose their next meal within their self-set daily food allowance, taste and nutrition goals. The user shortlists acceptable meals and deliberately picks a face-down card from those finalists. They can change the result. Current code reads Food discovery, selected-address menu data, existing cart totals and coupon descriptions, then hands checkout to Swiggy. It does not alter carts, apply coupons, place orders, import history, or invent unavailable nutrition. Planned conversational interpretation and independently sourced nutrition estimates are separate future work, subject to provider agreement and quality checks. [Current setup](../swiggy-setup.md), [product specification](../meal-planner-product.md)

The defensible product advantage is the decision flow, user-owned goals and explicitly saved preferences, transparent budget arithmetic, and a carefully validated nutrition layer built from appropriately licensed independent sources. Request permission before any enduring Swiggy-derived personalization. Do not pitch a harvested menu database, cross-provider data aggregation, competitive pricing intelligence, bulk order-history learning, advertising profiles, or training on provider data as the moat. The access ground rules prohibit competitive intelligence, unauthorized harvesting, misleading aggregation and scraping; consent alone does not override those restrictions. Provider-data analytics/training requires both explicit user consent and a DPA. [Application ground rules](https://mcp.swiggy.com/builders/access/), [data contract](https://mcp.swiggy.com/builders/docs/operate/data-and-compliance.md)

## Actual retained and processed data

- **Swiggy browser login:** phone/OTP entered only in Swiggy's authorization UI. Hungii does not collect those credentials. However the `get_addresses` schema explicitly includes `phoneNumber`, and order-details schemas include name, mobile and coordinates. The general compliance page's claim that tools return no raw personal identifiers conflicts with the specific schemas. Treat results as PII and rely on specific schema evidence; the current API removes the phone field before returning addresses to Android. History/order-details tools are present in the internal read allowlist but have no exposed application action. [Addresses](https://mcp.swiggy.com/builders/docs/reference/food/get_addresses.md), [order details](https://mcp.swiggy.com/builders/docs/reference/food/get_food_order_details.md), [data contract](https://mcp.swiggy.com/builders/docs/operate/data-and-compliance.md)
- **Hungii identity:** Google login requests `openid email profile` through Supabase. Supabase Auth therefore processes identity data even though Android retains a UUID and encrypted login tokens rather than a copy of the profile. This identity pipeline requires a notice and infrastructure/subprocessor review; an India function does not prove Google identity or voice processing stays in India. [Source: HungiiApi](../../android-prototype/app/src/main/java/com/hungii/prototype/HungiiApi.kt)
- **Server connection:** Hungii UUID, encrypted Swiggy token, token expiry, selected address ID and connection timestamp. Connect consent is required in code, but no policy-version/consent-timestamp record exists. Expired tokens and unused expired OAuth-state rows are not periodically purged. Disconnect retains credentials if upstream revocation fails; deletion/withdrawal must remain possible even when the provider is unavailable or a token has expired. [API](../../supabase/functions/hungii-api/index.ts), [migration](../../supabase/migrations/202610020001_hungii.sql)
- **Device favorites:** only after saving permission, Room persists selected dish/restaurant IDs and names, image URL, description, offer text, item price, diet flag, ETA and distance. This is selected provider data, not merely user-written notes. Delete/withdraw saves an empty favorites list; sign-out and Swiggy disconnect do not delete every owner's retained Room rows. Saved meal data is not sent by the tracker-sync call. Fresh menu/availability must be re-read before any eventual use for checkout. [Model](../../android-prototype/app/src/main/java/com/hungii/prototype/HungiiModel.kt), [Room storage](../../android-prototype/app/src/main/java/com/hungii/prototype/LocalStore.kt)
- **Tracker:** local user-entered budget, nutrition totals and goals; explicit server sync retains this state. Server accepts only named tracker top-level keys, but nested `intake` values are not semantically allowlisted. Do not portray this as a strong guarantee that arbitrary submitted nested data cannot be persisted. Privacy/deletion notices must cover Hungii's own tracker independently of Swiggy rights. [API](../../supabase/functions/hungii-api/index.ts)
- **Speech/AI:** check-ins use Android's default `SpeechRecognizer`; microphone permission is requested, but on-device recognition is not enforced and processor/region/retention are not established. There is no deployed LLM integration. External AI must not receive Swiggy menus, history, addresses or derived summaries before the required contract, transfer assessment and consent. User-authored content can itself contain sensitive or provider data; inspect/minimize rather than assuming a field label makes it safe. [Activity](../../android-prototype/app/src/main/java/com/hungii/prototype/MainActivity.kt), [data contract](https://mcp.swiggy.com/builders/docs/operate/data-and-compliance.md)

## Production gates and unresolved questions for Swiggy

1. Confirm staging Food and OAuth hosts, DCR registration/approval flow, permitted test accounts, seeded dataset and no-real-order guarantees. Supply the eventual exact HTTPS callback, including its region query, once infrastructure exists; ask whether static egress IPs are mandatory for staging and what alternatives are accepted. [Access](https://mcp.swiggy.com/builders/docs/operate/access.md), [application](https://mcp.swiggy.com/builders/access/)
2. Confirm persistent connection requirements for a serverless Mumbai adapter, inactivity/session TTL and how auth events count. The current dedicated rate-limit page says limits are enforced and reconnection per request is forbidden; the production checklist still says MCP-layer 429 is not enforced in v1.0. Dedicated quota guidance is the conservative working contract, not evidence we have verified active staging quotas. The header example even shows remaining 87 above limit 70. Ask for actual error/header fixtures and burst interpretation. [Rate limits](https://mcp.swiggy.com/builders/docs/operate/rate-limits.md), [production checklist](https://mcp.swiggy.com/builders/docs/build/ship-to-production.md)
3. Ask whether consented user-specific favorites may retain the current selected menu fields between sessions; what minimum fields, expiry, identifiers and lawful basis are permitted? Clarify history-assisted personalization separately. No approval is implied by implementing a consent checkbox. Ask how Hungii should learn of Swiggy-account deletion/revocation and meet derived-data deletion requirements. [Data contract](https://mcp.swiggy.com/builders/docs/operate/data-and-compliance.md)
4. Request applicable MCP integration/data-protection/privacy terms and DPA template. Confirm operator/developer track and Hungii's processor obligations for provider data, while separately assessing responsibilities for its own identity, goals and food log. Do not equate Swiggy's self-described DPDP posture or its NDA certifications with Hungii compliance or certifications. Final terms may add obligations absent from public docs. [Operate](https://mcp.swiggy.com/builders/docs/operate/index.md), [data contract](https://mcp.swiggy.com/builders/docs/operate/data-and-compliance.md), [application legal framework](https://mcp.swiggy.com/builders/access/)
5. Confirm acceptable Supabase Mumbai topology, CDN/log/backup/subprocessor treatment, and any outside-India speech/LLM proposal. The provider's compliance page permits its India/Singapore infrastructure boundary, while the overview more broadly says no cross-border flows. Do not promise absolute India-only handling based on either statement; declare Hungii's actual paths and negotiate DPA/transfer mechanisms before non-India provider-data processing. [Data contract](https://mcp.swiggy.com/builders/docs/operate/data-and-compliance.md), [overview](https://mcp.swiggy.com/builders/docs/start/what-is-swiggy-mcp/)
6. Confirm the meal-level shortlist/ranking/random-choice experience fits intended use, required attribution, permitted offer presentation and current cart/checkout limits. The ground rules prohibit manipulation of incentives, order flows or ranking systems; ask whether bounded personal reranking of returned meals and comparisons of legitimately returned eligible offers are permitted. Do not imply manipulation of Swiggy's rankings or incentives. Nutrition estimates must have independent documented provenance and uncertainty, with no guaranteed medical or ADHD benefit. Current menu schemas do not publish calories/macros. [Application ground rules](https://mcp.swiggy.com/builders/access/), [browse schema](https://mcp.swiggy.com/builders/docs/reference/food/get_restaurant_menu.md), [branding](https://mcp.swiggy.com/builders/docs/operate/support.md)
7. Before live users: deploy and verify actual Mumbai environment, add privacy/retention/deletion/consent evidence, fix persistent-session/rate handling, validate user isolation and callbacks, capture minimal support diagnostics, complete rollout/on-call runbook, and obtain ≥48 hours green staging plus explicit production confirmation. Report these as pending rather than asserting they are done. [Production checklist](https://mcp.swiggy.com/builders/docs/build/ship-to-production.md)

Operational contacts: `builders@swiggy.in` for access, rates, terms and documentation discrepancies; `security@swiggy.in` for vulnerabilities/security-relevant schema mismatches. Provide failing session IDs and timestamps, not full response bodies or tokens.

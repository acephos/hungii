## Persistent MCP client and rate controls

Current Swiggy [rate/session requirements](https://mcp.swiggy.com/builders/docs/operate/rate-limits.md) say MCP limits **are enforced**, including connection/initialization auth events: 70 requests/minute/user/server, 30 writes/minute, burst described as twice steady-state in a ten-second window. Keep one session per user, reuse initialization, initialize domains sequentially, stop attempts on block/rejection, honor `Retry-After`, and contact builders if blocked. The [production guide](https://mcp.swiggy.com/builders/docs/build/ship-to-production.md) contradicts enforcement by describing 429 as future behavior. Follow the dedicated current rate page conservatively; exact auth-event budgets, burst calculation and error/header fixtures remain questions for staging.

Pinned `@modelcontextprotocol/sdk@1.31.0` supports these contracts:

| Mechanism | Verified behavior | Implementation implication |
| --- | --- | --- |
| `Client.connect(transport, options)` | Performs MCP initialization; client is reusable for repeated calls. | Cache an initialized client per authenticated Hungii user and credential generation, coalesce concurrent connects, and cache validated tools. Never key ownership by Swiggy session ID. |
| `StreamableHTTPClientTransportOptions` | `requestInit`, `fetch`, `reconnectionOptions`, `authProvider`, optional `sessionId`. Transport getter returns session ID learned from `mcp-session-id`. | Custom fetch can capture safe headers before SDK strips them from errors; wrapper must enforce cooldown/block and per-user request budget. Supplied token should be tied to that user only. |
| `StreamableHTTPError` | Numeric `code` is HTTP response status; exception retains message, **not** Response/Retry-After headers. | Classify `code=429/401/419/5xx`; do not rely only on `.status`. Never log the raw message since POST errors include upstream body text. Capture Retry-After in custom fetch. |
| `reconnectionOptions` | SSE reconnection backoff defaults to 1s initial, 30s maximum, growth 1.5, two retries. Server SSE `retry:` can override the delay. | This is stream reconnection, not tool-call backoff or HTTP Retry-After support. `maxRetries:0` disables scheduled stream retries; alternatively gate every custom-fetch attempt after blocks. |
| `close()` vs `terminateSession()` | Close aborts transport and pending reconnection timer. Terminate sends MCP DELETE with session ID, accepts 405, clears ID, then closes. | Eviction closes locally; attempt protocol session termination when suitable. MCP DELETE does **not** replace Swiggy OAuth logout. Persistent reuse ends on disconnect, replacement credentials, shutdown or bounded idle eviction. |
| `Client.callTool(params, resultSchema?, options?)`, `listTools(params?, options?)` | Request options occupy third argument for `callTool`, second for `listTools`. | Pass `undefined` for default result schema before tool timeout options. Inspect tool failure envelopes separately from transport failures. |

## Timeout scopes

SDK `RequestOptions` supports `signal`, `timeout`, `resetTimeoutOnProgress` (false by default), and `maxTotalTimeout`. Default RPC timeout is 60,000 ms; without explicit `maxTotalTimeout`, progress-reset mode has no total maximum. RPC timeout/cancellation is distinct from transport lifetime. [Request declarations](https://unpkg.com/@modelcontextprotocol/sdk@1.31.0/dist/esm/shared/protocol.d.ts), [protocol implementation](https://unpkg.com/@modelcontextprotocol/sdk@1.31.0/dist/esm/shared/protocol.js)

Use one total wall-clock deadline for the user action covering queue wait, initialization, discovery, tool calls and delays, with bounded RPC attempts inside that deadline. Swiggy caps user-facing **total retries** at 30 seconds, limits transient backoff attempts, forbids reusing rejected auth tokens, and requires `Retry-After` rather than stacking rate waits onto exponential backoff. An excessively long Retry-After should return a retry-later UI instead of holding the user action open. [Production guide](https://mcp.swiggy.com/builders/docs/build/ship-to-production.md)

**Inference for implementation:** a transport-wide `AbortSignal.timeout(30000)` kills the reusable transport/SSE lifetime after 30 seconds. Avoid it. A custom-fetch timer can bound **time to response headers**, combined with the supplied transport signal, but should clear after `fetch` returns; RPC signal/timeout bounds response processing. Keeping a fetch timer active over an SSE response aborts a legitimate long-lived stream. Server/container/proxy shutdown and graceful drains need separate controls. This follows from the SDK's fetch, SSE-reader and lifetime abort-controller implementation, not a special Swiggy header-timeout specification. [Transport implementation](https://unpkg.com/@modelcontextprotocol/sdk@1.31.0/dist/esm/client/streamableHttp.js)

## Auth, disconnect and account deletion

Swiggy: browser OAuth 2.1 + PKCE S256, exact HTTPS callback, DCR client, per-user token. Access token lasts five days; refresh issuance is not implemented despite metadata; reauthorize on 401/419 or JSON-RPC `-32001`. `POST https://mcp.swiggy.com/auth/logout` with Bearer token revokes the Swiggy session, after which local token must be removed. Staging auth base and seed accounts need confirmation. Docs do not specify logout's expired-token response or revocation retry contract. [Authenticate](https://mcp.swiggy.com/builders/docs/start/authenticate.md), [delegated auth/logout](https://mcp.swiggy.com/builders/docs/start/enterprise/delegated-auth.md)

**Implementation decision:** local disconnect/deletion must remain effective when Swiggy revocation fails; erase local credentials and expose a truthful “remote revocation could not be confirmed” status with guidance to Swiggy account controls. Do not claim an upstream 401 proves every remote session was revoked. Clearing in-memory sessions and stale in-flight OAuth state is necessary; prevent concurrent callback/upsert from recreating a deleted connection.

Supabase `auth.getUser(jwt)` performs a server request and returns authenticated identity suitable for authorization. `auth.admin.deleteUser(id, shouldSoftDelete=false)` requires server-only service-role privileges and user UUID; it deletes via `/admin/users/{id}`. The caller's self-deletion must first validate its Bearer with `getUser(jwt)` and use the returned user's ID—never an ID supplied in the deletion body. Admin authority does not establish who the caller is. Hard deletion is the default; soft deletion is a separate irreversible hashed-identity mode, not a substitute for deleting Hungii tables. [getUser](https://supabase.com/docs/reference/javascript/auth-getuser), [deleteUser](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser)

Actual source verified locally: `@supabase/auth-js/2.117.2/src/GoTrueClient.ts` `getUser`/`_getUser`, and `src/GoTrueAdminApi.ts` `deleteUser`. Source links: [published client](https://unpkg.com/@supabase/auth-js@2.117.2/src/GoTrueClient.ts), [published admin](https://unpkg.com/@supabase/auth-js@2.117.2/src/GoTrueAdminApi.ts). Deleting Auth users invalidates refresh access but outstanding signed access JWTs can remain cryptographically valid until expiry; calling `getUser` on every Hungii API action checks live existence. Storage objects can prevent user deletion. Hungii FK cascades should remove linked rows, but test the real migration and purge process. [User management](https://supabase.com/docs/guides/auth/managing-user-data)

## Runtime decision

Supabase hosted Edge Function workers have finite lifetime: free 150 seconds, paid 400 seconds; an isolate may serve multiple requests but can also retire early when work is considered complete. A global `Map` provides best-effort reuse during one isolate only; `waitUntil` cannot extend hard lifetime. Therefore it cannot promise one enduring MCP client per user. [Limits](https://supabase.com/docs/guides/functions/limits), [worker lifecycle](https://supabase.com/docs/guides/troubleshooting/edge-functions-worker-timeouts-and-websocket-drops)

Deno supports self-hosted VM/container execution, environment secrets, and HTTP serving. Existing explicit `Deno.serve(...)` code runs with `deno run`; `deno serve` instead expects a default fetch-handler export. Use an actual long-lived process behind HTTPS rather than assume the hosted function lifecycle disappears because the source is Deno. [Self-hosting](https://docs.deno.com/runtime/deploy/), [Docker](https://docs.deno.com/runtime/reference/docker/), [serve vs run](https://docs.deno.com/runtime/reference/cli/serve/)

**Architecture inference:** a single supervised container in AWS Mumbai can own a bounded in-memory session pool while retaining Supabase Mumbai Auth/Postgres. This is one technical option, **not a hosting requirement or authorization to spend money**. Declare configured region, verify host placement independently, remove dependence on the Edge-only `SB_REGION`, and expose a real HTTPS callback route. No provider preference for Edge Functions was found. Supabase path/`forceFunctionRegion` controls apply to hosted functions, not arbitrary container hosts. Multiple processes/replicas would fragment ownership unless user affinity or a single session service is implemented; `deno serve --parallel` would have the same issue. Idle eviction, restart budget, draining, token invalidation and pool size limits remain required. Region environment strings and local Docker startup are not proof of deployed residency. [Deno runtime deployment](https://docs.deno.com/runtime/deploy/), [Swiggy session hygiene](https://mcp.swiggy.com/builders/docs/operate/rate-limits.md)

## Free-only alternative: durable logical HTTP session

Additional protocol review after the user required zero spending: a long-lived SDK object is **not synonymous with a long-lived MCP logical session**. A separate container is unnecessary if Swiggy supports the standards-compatible durable logical-session path below. This is a candidate for implementation and staged validation, not proof of Swiggy approval.

The official 2025-06-18 [Streamable HTTP specification](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports) defines a session as logically related interactions. Every JSON-RPC message is a separate POST. If initialization returns `Mcp-Session-Id`, include it on subsequent requests; also include the negotiated `MCP-Protocol-Version`. POST requests must accept both JSON and SSE responses. GET SSE is optional; servers can return 405. SSE responses may close after their matching response. Session-bearing 404 requires a new initialization without the old ID. A client should explicitly DELETE a session it no longer needs, allowing 405. These requirements do not impose one uninterrupted TCP connection across the session.

Initialization must precede operation, negotiate a supported protocol version and capabilities, and be followed by `notifications/initialized`. Subsequent operation respects that negotiation. An unsupported returned protocol must fail rather than be guessed. Lifecycle language says HTTP shutdown closes associated connections, while transport session management allows related separate HTTP requests; neither establishes Swiggy's TTL or billing behavior. [Lifecycle specification](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)

**Design inference:** preserve encrypted per-user/provider-session state in server-only Mumbai Postgres: session ID, negotiated version/capabilities, validated tool schemas, connection generation, bounded expiry and rate cooldown. Later Edge workers directly POST `tools/call` under the saved session instead of constructing an SDK `Client` and invoking its automatic initialize. Always send that user's Bearer token; never fabricate an ID. Reuse the session until actual expiry/error/disconnect. If no session header is issued, treat the server as stateless and ask how Swiggy identifies a reusable logical session. Cached metadata needs bounded refresh and schema-change handling. Direct HTTP must correctly parse SSE framing and matching request IDs, account for notifications/server messages and cancellations, bound response size/time, and sanitize upstream errors. Do not modify SDK private fields to pretend it was initialized.

Swiggy forbids a new initialize per tool and requires persistent per-user sessions, but says auth happens once per connection and reconnects count as auth events. It does not explicitly establish whether valid-ID POSTs from different Edge isolates or TCP connections trigger another auth event, nor whether GET must stay open. Confirm cross-worker session reuse, idle TTL, credentials/session binding, required notifications, possible affinity requirements and accounting through authenticated staging/support before declaring provider compliance. [Swiggy session guidance](https://mcp.swiggy.com/builders/docs/operate/rate-limits.md)

### Atomic ownership across Edge workers

Postgres row locks and transaction advisory locks release when the transaction ends. Thus a locking RPC does not keep its lock over the subsequent Swiggy HTTP call. Use an atomic database claim to store a lease owner nonce, `lease_until`, connection generation and initialization phase; completion must conditionally match that lease/generation. A deleted/replaced connection must reject stale completion. This is a design inference from transaction-lock semantics. [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html)

The RPC can serialize claims using `SELECT ... FOR UPDATE`/conditional updates, perform one atomic quota check/update, and release ownership on success/failure with fencing. Limit lease duration and wait budgets. Crash after remote initialize but before database persistence can orphan a remote session; database leases alone cannot guarantee exactly-once network initialization. Recover conservatively with bounded cooldown and stop on blocks rather than retrying initialization indefinitely. Test concurrent claims, lost responses, lease expiry, provider 404/429, disconnect during initialization and worker restarts.

Supabase supports SQL/PLpgSQL functions through `rpc()`. For privileged session/lease functions, restrict execute to server-only authority, explicitly fix `search_path` and qualify tables; default function privileges are broad. Authentication must already establish the caller's Hungii ID. [Database functions/security](https://supabase.com/docs/guides/database/functions)

### Free Supabase envelope

As of review, Free is $0/month with two active projects, 500 MB database, 50,000 MAU, 5 GB egress and one-week inactivity pausing. Stay on Free; no paid plan, paid compute, add-on, or spending authorization follows from the architecture. Capacity pauses and quota limits constrain production availability. [Pricing](https://supabase.com/pricing)

Free Edge includes 500,000 invocations; docs do not list paid overage for Free. Worker lifetime remains 150 seconds with 2 seconds CPU/request and 150-second request idle timeout. Durable DB session records survive worker termination, while each bounded interactive HTTP operation must fit the runtime. [Function pricing](https://supabase.com/docs/guides/functions/pricing), [limits](https://supabase.com/docs/guides/functions/limits)

Mumbai `ap-south-1` is supported. Set `x-region` or `forceFunctionRegion`, verify response `x-sb-edge-region`/runtime `SB_REGION`, and select a Mumbai database project. The docs do not describe a paid-only gate for regional invocation. Validate the actual free project and gateway/log/subprocessor paths rather than infer whole-system residency. [Regional invocation](https://supabase.com/docs/guides/functions/regional-invocation), [database regions](https://supabase.com/docs/guides/platform/regions)

Supabase Cron uses `pg_cron`, can run SQL/functions and records jobs/status; enable it in Dashboard or with `create extension pg_cron`. Use a bounded database-local expiry/deletion job, not remote warmup calls to keep MCP sessions alive. The installation docs impose no paid-only prerequisite; confirm successful enablement in the actual Free project. Cron execution still consumes shared database resources, and a paused project cannot guarantee scheduled purges. Purge expired records on access as well, with a documented inactivity/deletion procedure. [Cron overview](https://supabase.com/docs/guides/cron), [installation](https://supabase.com/docs/guides/cron/install)

This provides a plausible free-only protocol design to build and test. Full production readiness still needs real Google/Supabase setup, signed terms where applicable, approved callback, authenticated Swiggy staging evidence, 48 hours green and production approval. Neither free infrastructure nor passing local protocol tests can establish those externally controlled facts. [Production checklist](https://mcp.swiggy.com/builders/docs/build/ship-to-production.md)

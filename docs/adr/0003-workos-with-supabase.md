# WorkOS with Supabase

Accepted 2 October 2026 at the founder's request. Kotlin/Compose and the Supabase Free Mumbai database/Edge runtime remain. WorkOS AuthKit staging supplies Hungii email sign-in; Swiggy remains a separately consented provider connection. No Google app OAuth client, SMS login, paid SSO, custom auth domain or paid runtime is required.

Android opens hosted AuthKit in a browser with PKCE S256, a random state and a ten-minute pending flow. Its public-client authorization-code exchange includes no API secret. The rotating refresh token is encrypted with Keystore; access tokens live in memory. Refresh uses a Mumbai server endpoint holding the staging WorkOS key. The documented Android SDK currently requires Kotlin 2.4; this Kotlin 2.1.20 prototype uses the documented HTTPS protocol via its existing OkHttp client.

The Edge handler verifies RS256 JWT signatures, exact issuer, current application's client ID, subject/session/expiry and absence of impersonation. It also checks the live WorkOS session before every account action, so revocation invalidates an otherwise unexpired JWT. WorkOS issuer identifies the environment's default application; client_id identifies Hungii Android. Authentication failures return sign-in-required; service outages fail closed.

A hash of client ID plus verified WorkOS subject resolves a backend-only Hungii UUID. No email linking or WorkOS subject is copied into the database. Postgres tables are private and server-authorized, rather than exposing direct Data API access with a WorkOS JWT. Therefore this architecture does not require Supabase's third-party Auth registration or authenticated-role JWT template. If direct Data API/Realtime access is added, configure the official integration and design WorkOS-aware RLS first; auth.uid() cannot represent the non-UUID WorkOS subject.

Confirmed deletion atomically marks the account deleting and erases tracker/provider state. Row-lock/trigger fences block writes racing deletion. WorkOS user deletion follows; a failure leaves a retryable deleting account, without restoring erased data. Successful deletion retains only a hashed identity fence for 24 hours to stop previously authorized in-flight requests from recreating an account. Scheduled/access purge removes the fence. No existing Supabase account is silently linked by email.

Version 0.6 adds an account entry screen with a persistent local-only choice, optional per-device cloud sync for user-authored profile/goals/totals/filters and automatic restore. A private Postgres compare-and-save RPC protects server revisions, including the absent-row case, so two devices cannot silently replace each other's changes. Local dirty edits survive restart; conflicts offer cloud/local choices. Declining or stopping sync survives restart. Provider meal shortcuts are excluded from this cloud schema.
